# 18. モデルの説明表示と、AI サポートによるモデル提案(v0.10)

> ステータス: 🟢 承認済み(2026-11-19。Q-74〜80 は推奨どおり)。
> **経緯**: モデルが増えた(16・17)ため、ユーザーから「生成画面でモデルを選ぶとき、そのモデルの用途・得意不得意などの説明を見られるようにしたい。AI サポートもそれを把握して、依頼に合うモデルを提案できるように」との指示(2026-11-19)。16・17(M12・M13)は同日に承認済み。本資料は、それに **追加する** 機能。

## 1. 目的とスコープ

1. 生成画面でモデル(種別・ファイル)を選ぶと、**そのモデルの用途・得意/不得意・プロンプトの書き方・推奨設定・必要なメモリ・対応機能** が分かる(「モデルの説明」)。
2. **AI サポート(F-13)がモデルの特徴を把握** し、依頼(例:「実写っぽい風景」「アニメで 2 人を描き分けたい」)に合うモデルを **理由つきで提案** できる。導入済みかどうかも踏まえる。

**やらないこと**: モデルの自動判別(ファイルの中身・名前からの推定)、モデルの性能測定、ユーザーによる説明文の編集(§9 Q-75)、画像・プロンプトの送信を増やすこと。

## 2. 方針: 説明は「カタログ」に 1 か所で持つ(単一の情報源)

- 説明(プロフィール)は、モデル取得カタログ(12 §4)の **ファミリーごとに持つ**。生成画面の説明パネル、取得ページ、AI サポートのシステムプロンプトは、**すべて同じデータから作る**(更新漏れ・食い違いを防ぐ。13 §4.3 の方針と同じ)。
- SD1.5 / SDXL / Flux / Flux GGUF / NoobAI-XL / Animagine XL 4.0 / Anima / Qwen-Image 2.1 / Krea 2 のすべてのファミリーに、プロフィールを **必須** とする(カタログのテストで、無いものは失敗させる)。
- 内容は **配布元の説明(モデルカード・公式ドキュメント)に基づく**。根拠を確認できない項目(特に NSFW 対応)は書かない。表示には「配布元の説明に基づく目安」と添える。

## 3. データ(12 §4.1 のスキーマに追加)

`ModelFamily` に必須フィールド `profile` を追加する(`schemaVersion` は 2 に上げる。カタログはアプリ同梱のため移行は不要)。

```ts
interface ModelProfile {
  summary: { ja: string; en: string };            // 1 行の用途「アニメ・イラスト向けの汎用 SDXL」
  style: ("anime" | "realistic" | "illustration" | "general")[];   // 絵柄の傾向
  bestFor: { ja: string[]; en: string[] };        // 得意(各 1 行、最大 4 件)
  weakAt: { ja: string[]; en: string[] };         // 不得意・注意(各 1 行、最大 4 件)
  promptStyle: { kind: "tags" | "natural" | "both"; hint: { ja: string; en: string } };
                                                  // 例 tags:「Danbooru タグ(1girl, solo, …)」
  recommended: { steps: number; cfg: number; sampler?: string; scheduler?: string;
                 size: { width: number; height: number } };   // 「推奨設定を適用」の値
  resources: { vramGb: number; speed: "fast" | "medium" | "slow" };   // 目安(GB は最小の目安)
  nsfw: "capable" | "limited" | "not-intended" | "unknown";   // 配布元の記載で確認できたものだけ capable / limited
  sourceNote: { ja: string; en: string };         // 「配布元の説明に基づく目安」+ 取得元名
}
```

- **対応機能(顔補正・ControlNet・Inpaint・ネガティブ・画像サイズの上限)は、データに持たず、種別(`ModelKind`)から計算する**(10 §7・17 §3 の規則が正。二重管理しない)。
- 推奨値は 16 §5 の組み込みプリセット・17 §4 の既定値と **同じ定数を参照** する(値の食い違いを防ぐ)。
- ファミリーの `usedBy` や `tags`(16)とは独立。`tags` は取得ページのフィルタ用、`profile` は説明用。

## 4. 導入済みファイルとプロフィールの対応づけ

- 導入済みのファイルは、**カタログの `fileName`(固定)との一致** でファミリーに結び付ける(12 の検出の仕組みを再利用。ハッシュの照合は不要で、ファイル名のみ)。
- **カタログ外のファイル(手動で置いたもの)**: ファミリーが分からないため、**種別(`sd15` / `sdxl` など)の一般的な説明** を表示し、「カタログ外のモデルです。得意・不得意は不明」と明示する。種別ごとの一般説明も `profile` と同じ形で持つ(SD1.5 / SDXL / Flux のファミリーの説明を流用する)。
- 同一ファイル名で別のモデルを置く場合などの誤対応は、説明に「ファイル名が一致した場合の目安」と添えることで許容する。

## 5. 生成画面の UI(05 に追記)

- **モデル選択の候補に、短い補足を付ける**: 各候補に、絵柄のバッジ(アニメ / 実写 / 汎用)と、必要なら「重い」「NSFW 対応」のバッジ。カタログ外は「カタログ外」。
- **選択中のモデルの「モデルの説明」パネル**(折りたたみ可。既定は展開。開閉は端末に記憶)を、モデル選択欄の直下に置く:
  - 用途の 1 行(`summary`)、**得意 / 不得意**(箇条書き)、プロンプトの書き方(`promptStyle.hint`)、必要メモリ・速度の目安(`resources`)、**対応機能**(顔補正・ControlNet・Inpaint・ネガティブ。○ / ×。種別から計算)、NSFW の表示(`capable` / `limited` のときのみバッジ。`unknown` / `not-intended` は表示しない)、出典(`sourceNote`)。
  - **[推奨設定を適用]** ボタン: `recommended` をフォームへ反映する(ステップ・CFG・サンプラー・サイズ。プロンプトは変えない。確認なしで適用し、取り消しは既存の「元に戻す」と同じ扱い)(Q-77)。
  - **[AI に相談]** ボタン: AI サポートのパネルを開き、「このモデルは今の目的に合いますか?」と入力欄に仮入力する(送信はユーザー操作)。
- 取得ページ(`/models`)の各ファミリーにも **同じ説明の部品** を使う(「バージョン」の選択と並べて、得意/不得意が分かる)。
- 未接続・モデル未導入のときの空状態では、**取得ページの説明で選べる** ことを案内する。

## 6. AI サポートでのモデル提案(11・13 §4 の拡張)

### 6.1 機能カタログへの追加(`services/assistant/capabilities.rs`)

- **「モデルガイド」節** を、§3 のプロフィールから **自動生成** してシステムプロンプトへ連結する(手書きで二重に持たない)。1 ファミリーあたり 1〜3 行に圧縮: 名前、用途、得意、不得意(最重要 1〜2 件)、プロンプトの書き方、必要メモリ、NSFW(`capable` / `limited` のみ)、対応機能。
- **提案のルール** をプロンプトに明記する: 依頼の目的(絵柄・人数・文字・NSFW・速度・メモリ)に合うモデルを **1〜2 件、理由つき** で挙げる/導入済みのものを優先し、未導入なら「取得ページで導入できる」と案内する/メモリ不足が見込まれるなら軽いモデルも添える/**ガイドに無いモデルを推測で勧めない**(「カタログ外」と区別して答える)。
- プロンプトの長さの上限を **6,000 → 9,000 文字** に引き上げる(13 §4.3(c)。プロンプトキャッシュにより入力コストは抑えられる)(Q-78)。モデルが増えて上限を超えるときは、各ファミリーの記述を短くする(上限の引き上げを繰り返さない)。

### 6.2 現在の状態として渡すもの(11 §3 のスナップショットに追加)

- `model`: `{ kind, familyId | null }`(選択中のモデルのファミリー ID。カタログ外なら null)。**新しく追加するフィールドはファミリー ID だけ**(ファイル名・パスは含めない)。なお、既存のスナップショット(11 §3)の `model.name` には選択中のチェックポイントのファイル名が従来どおり含まれる(同意ダイアログの「選択中のモデル名」に記載済み)。
- `installedFamilies`: 導入済みのファミリー ID の配列(例 `["sdxl-base", "noobai-xl"]`)。**ファイル名・パスは送らない**。直近のモデル一覧の取得結果から作り、通信はしない(未取得なら添えない)(Q-76)。
- 追加で外部へ送られる内容は、**ファミリー ID(カタログの固定の識別子)のみ**。同意ダイアログの説明(11 §5)に「導入済みのモデルの種類(名前の識別子のみ)」を一文追記する。

### 6.3 モデルの提案を、ユーザーが 1 クリックで反映できるようにする

- `suggest_params` のホワイトリスト(11 §6)に、新しい提案の種類 **`suggest_model`: `{ familyId: string, reason: string }`** を追加する(Q-77)。
- 提案カードに、導入済みなら **[このモデルに切り替える]**(モデル種別・ファイルを切り替え、§5 の説明パネルが更新される)、未導入なら **[モデル取得ページで開く]**(`/models?family=<id>`)を出す。**切り替えは必ずユーザーのクリック** で、AI にアプリを操作させる手段は持たない(13 §4.4)。
- `familyId` は **カタログに存在する ID だけ** を受け付ける(それ以外の値は捨てる。11 §6 の検証と同じ)。
- 既存の提案(ステップ・CFG など)との併用: モデルを切り替えると、その種別で使えない項目(ネガティブ、顔補正など)が変わるため、**モデル提案と数値の提案は別のカードにして、切り替え後に数値提案を再確認させる**。

## 8. テスト・検証

- Rust: カタログの全ファミリーに `profile` があり、各項目の件数・長さが規則内であること。`system_prompt()` が **全ファミリーのモデルガイドを含み**、9,000 文字以内であること。`suggest_model` の `familyId` がカタログ外なら捨てられること。スナップショットに **ファイル名・パスが含まれない**こと。
- フロント(Vitest): モデルの選択で説明パネルが更新されること、カタログ外の表示、推奨設定の適用で値が反映されること、NSFW バッジが `capable` / `limited` のときのみ出ること、提案カードの出し分け(導入済み / 未導入)。
- 実機: 実際の Anthropic API で、「実写の風景」「アニメで文字入り」「軽いモデルで」などの依頼に対し、妥当なモデルが理由つきで提案されることを確認する(09 に記録。未確認なら明記する)。

**マイルストーン M14**: ① `profile` のスキーマとカタログ(既存の SD1.5 / SDXL / Flux と、M12 の NoobAI-XL・Animagine XL 4.0)・説明パネル・推奨設定の適用 → ② AI のモデルガイドと `suggest_model` → ③ M13 の各種別(Anima・Qwen-Image 2.1・Krea 2)の追加時に、それぞれの `profile` を含める。M12 と並行して進められるが、**スキーマ(`schemaVersion: 2`)は M12 のカタログ追加より前に入れる**。
